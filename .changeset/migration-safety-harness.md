summary: Migration safety harness — transactional backup/verify/rollback bracket for every store move (saga T13339)
---

Every CleoDocs re-architecture store move (the T13360 migration, the T13361/T13362 legacy retirements) now wraps its steps in one reusable harness instead of hand-rolling per-migration safety. `runMigrationSteps` executes each registered step (`{ name, run, destructive?, verify? }`) inside a fixed bracket: a pre-step `VACUUM INTO` snapshot registered as a `migration` system backup whose `<backupId>.meta.json` sidecar is the step's backup receipt, then `BEGIN IMMEDIATE`, then the before-fingerprints, the step body and verification inside that single-writer transaction, then `COMMIT` only when every check passed — otherwise `ROLLBACK`, so a failed, refused or throwing step is never visible in the live store (T13609) and a concurrent writer can neither interleave with the bracket nor be silently discarded by a later restore. Rebuild recipes use `PRAGMA defer_foreign_keys` (enforced at COMMIT); `foreign_keys=OFF` is a no-op inside a transaction, and DROP of an FK-parent table records a sticky deferred violation at its implicit DELETE, so parent rebuilds use the save/null/restore recipe for their referencing children.

Verification compares per-table row counts before/after (a delta must be explained by the step's declared `expectedDelta`), content-hash spot checks (an order-independent multiset hash tolerant of integers beyond 2^53, sampled to 200 rowids on tables larger than the sample size, so a verbatim T11649 table rebuild still matches), and `PRAGMA foreign_key_check` (must return zero rows). Extension-backed tables that cannot be read on a connection (e.g. `vec0` without sqlite-vec) are reported as skipped, never silently trusted; every other read error fails the step (fail-closed). A failed verification auto-halts the runner, names the failed step, and leaves the restore path ready as the backstop: the halted step's report carries the backup receipt and pre-step fingerprints that `rollbackMigrationStep` consumes to restore the snapshot through the programmatic core of `cleo restore backup` (T13240) and re-prove counts, content hashes and file bytes against the pre-step snapshot.

Destructive steps refuse to run without `force: true` plus a backup receipt younger than the step start — guaranteed by construction, because the harness takes the snapshot before the guard runs. Proven two ways: (1) a real-shaped store at scale — the test seeds the actual T13354 conduit-history tables with thousands of rows plus blob files, runs a no-op rebuild of one history table through the harness, and rolls back with byte/count equality; (2) AC5's snapshot proof — a `cleo backup add` snapshot of this repo's real 1.34 GB `.cleo` store (207 tables, ~1.35 M rows) copied into a sandbox and run through the harness with a no-op step and a verified rollback, byte-identical to the pre-step snapshot (16 tests, all green; raw-write gates 28/38 clean in PR mode).
