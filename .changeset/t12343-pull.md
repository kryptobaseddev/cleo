summary: Sync pull - stage and apply a stream's verified segments, never a transaction twice (S5-1)
---

A store can now pull its stream's journal (journal spec §3.1, §2.8; T12343 S5-1).

- **`pullStream(db, …)`** (`store/sync/pull.ts`) pages through the stream after the store's persisted cursor. For each page, in one
  local transaction:
  - **Decode:** `deflate-raw` canonical JSON of `LedgerTxn[]`, parsed with the ledger schema. A vault count-delta segment
    (`cleo-vault-delta/v1`) carries no ops and is passed over.
  - **Verify:** every transaction's signature is checked against the segment's device key, before anything of the page is written.
    A bad signature or a malformed body refuses the segment (`SegmentRefusedError`).
  - **Deduplicate:** every transaction id already staged from the stream is skipped (`_sync_seen_txn`), so a re-delivered
    transaction is never staged or applied twice and a counter delta never doubles.
  - **Stage and advance:** the rest are staged, and the cursor advances (`_sync_cursor`).

  Then the applier applies, in stream order, own echoes included (they feed the fast path and the scoped rebase).
- **`pullSyncStream(opts)`** (`cloud/nexus-vault.ts`) wires `pullStream` to the journal client and the trusted device keys. It refuses
  a store bound to another replica than the link. A store with no pull position starts after the checkpoint it last synced (its
  genesis, or the snapshot it restored), seeded from that checkpoint's signed replica map.
- **New sync-journal migration** `t12343-pull-cursor`, local-only: `_sync_cursor` and `_sync_seen_txn`. Both are cleared from vault
  bundles, so a restored store resumes from its own checkpoint.
