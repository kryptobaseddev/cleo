A store past its genesis can now push its change journal (journal spec §2.8, §2.9, §1.3; T12343 S4-2).

- **`pushStream(db, …)`** (`store/sync/push.ts`) runs these steps in order:
  1. **Preconditions:** push is on, the stream is cut, and its genesis checkpoint is stored. No segment ever precedes the checkpoint
     it extends.
  2. **Local clock check:** if this device's clock runs more than `MAX_DRIFT` (5 min) ahead of the server's, push pauses and
     records `sync.clock_ahead` for `cleo doctor`. The offset is measured when the server's `Date` arrives, so later time never
     counts. Local writes are never refused, and the key clears once the clock recovers.
  3. **Server-authoritative rollback check:** a later segment from this replica on the server than the store ever persisted means
     the store was restored or copied behind it. Nothing is sent; it must rebind (T12753).
  4. **Seal and pack:** pending captures are sealed (at most 8 passes, so steady writers never hold the push back), then packed
     into persisted segments. The device registry's high-water mark
     advances after each persist.
  5. **Upload:** the persisted bytes are uploaded, lowest `replicaSeq` first, one at a time. A duplicate counts as stored, and a
     failed upload is resent with the same bytes next run.
- **`pushSyncStream(opts)`** (`cloud/nexus-vault.ts`) wires `pushStream` to the journal client:
  - `sealSegment` and `push` with the persisted bytes;
  - the device's transaction signatures;
  - the server's clock offset (the new `Http.lastServerOffsetMs`, measured at receipt);
  - E3's `replica.lastReplicaSeq` (project streams);
  - the device registry.

  It refuses, with nothing sealed or sent, when the store's bound replica is not the one the stream knows (T13304); push would
  otherwise seal as one replica and never select the other's transactions. A segment conflict maps to `E_NEXUS_SYNC_REFUSED`
  with the rebind remedy. `cleo cloud sync` (T12996) will call it.
