## 0. Read this first — the one thing that will mislead you

A causal claim was made on 2026-09-17 and shipped into the codebase, the
CHANGELOG and a workflow comment that sizes a config value:

> *"`@cleocode/cleo` is 80.6 MB; npm queues packages that large for
> asynchronous processing and returns exit 0 immediately; that is why v2026.9.6
> published but never became installable."*

**It is false.** Do not rebuild it. Three independent measurements:

| evidence | result |
|---|---|
| Six consecutive releases (9.1–9.6) at a **byte-identical** 80.6 MB / 1059 files | publish→available ranged **4m55s to 55m11s**. Size varied by zero; delay varied **11×** |
| v2026.9.7 cut the package 60% to 32.1 MB / 728 files | **2h55m09s** — 3.16× LONGER at 40% the size |
| Same v2026.9.7 run, same token, same minute: `@cleocode/core` (42.8 MB, **5319** files — larger, 7× the files) | **3m47s**, while `cleo` took 175m |

The sibling control also eliminates account throttling, registry incidents,
rate limits, OIDC config, time-of-day and publish order. `bin` entries are out
(`lafs`, `caamp`, `cleo-os`, `animations` all declare binaries and are fast) and
download volume is out (`core` outranks `cleo`, 234/wk vs 122/wk, and is fast).

**The failure reason is `metadata 404`, not `tarball 404`** — the per-version
document itself does not exist for hours, while a signed Sigstore provenance
attestation for that exact version already does. So this is not CDN propagation
of a published artifact; the write has not landed. It is package-specific and
on npm's side. See gh#1478.

The corrected text now lives in `packages/cleo/scripts/copy-studio-dist.mjs` —
it **records the correction** rather than deleting the claim, specifically so
the reasoning cannot be re-derived from the same intuition.

**Any future size work must be justified as install-time download/disk cost
only.** The 48.5 MB reduction in #1473 was always a good optimization; it was
only ever mislabelled as a fix.

### #1481 — the gate that never once ran

**47 runs, 47 failures, 0 successes since v2026.6.10.** It died in the build
step every time, so it never reached its own size assertion. Nobody knew whether
`@cleocode/core` was under its 30 MB budget.

Two causes, and the first hid the second:

1. **The pnpm filter ellipsis was inverted.** Trailing `pkg...` = package + its
   DEPENDENCIES; leading `...pkg` = package + its DEPENDENTS. T11976 switched
   both filters to the leading form *and wrote a comment asserting the opposite
   meaning* — which is why it survived 47 runs.
2. **Correcting the direction moved the failure, it did not fix it.** No pnpm
   filter can order this graph, because `core → adapters → caamp → core` is a
   real production cycle (pnpm names it in the log). A topological sort does not
   exist. **That cycle is why `build.mjs` exists.** The gate now runs the same
   build the release runs.

First green run printed the number nobody had seen:
`@cleocode/core packed: 11.97 MB / budget 30 MB`. **No threshold change needed
— the budget was never in danger, the gate was broken.**

### #1484 — the 3-second penalty on every write

Two independent causes of `event loop still alive 3000ms after teardown (held
by: PipeWrap×2, TCPSocketWrap)`:

1. `shutdownBrainWriter()` sets `_manager = null`, discarding that manager's
   `shuttingDown` flag. A later write constructs a **fresh** manager with the
   flag `false`, so a worker realm spawns *after* teardown. Guarded at
   **acquisition** with a module-scope latch (module scope precisely because the
   manager that would hold the flag is what gets discarded). **Also closed a
   listener leak nobody had noticed:** that block registered three
   process-lifetime handlers every time it ran.
2. `DIALECTIC_DEADLINE_MS` is 10s, `EXIT_BACKSTOP_MS` is 3s. **Unrefing the
   timer does not unref the socket.** New `packages/core/src/teardown-signal.ts`
   (three functions) is called as step 0 of `shutdownCliRuntime`.

> **Not claimed:** that the penalty is gone end to end. That needs an
> absence-of-string check over N runs of each affected command **in CI or on a
> `/home` clone** — `/mnt/projects` is fuseblk and runs git 23–49× slower than
> `/home`, so **no timing taken on that checkout is evidence about code.**

### #1483 — the verdict is binding and outlives the run

v2026.9.6 and v2026.9.7 both concluded `success` over a package that did not
exist. The pipeline had **already measured it correctly and written it to an
artifact** — `{"verified":false,"reason":"metadata 404"}`, `"failed": 1` — and
`continue-on-error: true` discarded it.

The split that resolves the old comment's legitimate worry: a run conclusion is
stamped once and never revised, but `cleo` has taken 4m55s → 2h55m. So the
**run** answers *"did this run prove installability inside its budget?"* and a
**cron-watched GitHub issue** answers *"is it installable now?"*.

Three outcomes, not two. The `pending` annotation is the anti-false-alarm
mechanism and says so explicitly: *this red means the run did not PROVE
installability, not that the release is broken — do not roll back, re-tag,
re-publish or bump.*

### #1482 — a size budget with floors

`scripts/assert-cleo-tarball.mjs` is a **presence** gate — every assertion is
`existsSync`, so re-adding the 48.5 MB would make all of them *more* true.

**Floors matter more than the ceiling.** A ceiling-only gate is green on an
*empty* package — the exact T12011 defect. It also **refuses to measure a dev
tree** (`E_DEV_TREE`): local `dist/` is tsc output (320 `.js`, 320 `.d.ts`, 640
`.map`) while CI publishes a 2-file esbuild bundle; `npm pack --dry-run` locally
reports 2006 files against the 728 that ship.

## 2. Traps you will hit

### `scripts/lint-postdeploy-budget.mjs` anchors on a COMMENT

`extract()` does `src.indexOf('Post-Deploy Execution Payload')`, which matches
the **comment banner** above the job — *not* its `name:` — then takes the first
`timeout-minutes:` after it.

- **Do not rename** that job or its banner.
- **Do not add any `timeout-minutes:`** between the banner and the job's own.
- Appending new jobs at the **end** of `release.yml` is safe. Inserting before
  silently retargets the linter onto the wrong number.

### Deep imports from `@cleocode/core` take no `.js`

Core's `./*` export maps to `./dist/*.js`, so the extension is supplied by the
pattern. `@cleocode/core/teardown-signal` resolves;
`@cleocode/core/teardown-signal.js` resolves to `dist/…js.js` and fails.

### `@task T####` references collide — six measured instances

I wrote `@task T12243`/`T12244` into new source before those rows existed. **Both
were real, unrelated tasks.** The fix is **create-then-read-back**:
`cleo add … --field /data/created/0`, then write the returned ID. Never write an
ID you have not read back.

### `$?` after a pipe is the LAST stage's status

`node script.mjs | tail -5; echo $?` reports `tail`'s exit code. Bit me once this
session (gh#1459).

### `gh run view --log` serves ZERO BYTES

Use `gh api repos/:o/:r/actions/runs/<id>/attempts/<n>/logs > x.zip`. An empty
log fetch is an **instrument failure**, not "nothing to report."

### `npm view <pkg> time --json` dates CREATION; polling dates OBSERVATION

The gap is however long you were not looking. Two agents misreported this by 48
minutes.

### BRAIN tables live in `.cleo/cleo.db`, not `.cleo/brain.db`

`.cleo/brain.db` has **no tables**. `brain_observations` is in `cleo.db`
(post-E6 consolidation).

## 3. Verification discipline that caught real problems

**Predict the failure COUNT before running the unfixed arm.** Twice this session
the count disagreed with the prediction and both times it was informative:

- execute-payload: predicted 7 failures, got **8**. The extra was a test that
  also asserted a field absent from the old code.
- T12239: predicted 4, got exactly 4 — with the one designed to be
  green-in-both staying green (it proves the late write is not silently
  dropped, the failure mode a careless fix introduces).

**Make the oracle a DIFFERENT KIND of question.** The T12239 tests assert on
**process listener counts**, not "was a Worker constructed" — because
`resolveWorkerPath()` returns null under vitest, so everything falls inline and
a "no Worker" assertion **would pass against the broken code**. That would be a
restatement of the harness, not a regression test.

### The watcher's cron has never fired — READ THIS BEFORE TRUSTING #1495

`release-installability-watch.yml` is `state=active`, on `main`, with
`schedule: '3-59/10 * * * *'`. In the ~55 minutes after v2026.9.8 published it
fired **zero times** — six missed windows. The only runs are the
`workflow_dispatch` from `release-verdict` and one I triggered by hand.

**The watcher's logic is fine** — dispatched manually it correctly reported
`#1495 v2026.9.8: 17/18 — pending cleo(metadata)` and **edited the issue body**
rather than commenting, which is the non-first-run path I had not exercised.
Only the trigger is missing.

Likely GitHub-side: newly-added `schedule` triggers commonly take time to
activate, and scheduled runs are delayed or dropped under load. But **until a
scheduled run actually appears, #1495 only updates when someone dispatches it**

that looks like it is watching and is not. Verify with:

```bash
gh run list --workflow=release-installability-watch.yml --limit 10 \
  --json event,createdAt --jq '.[] | "\(.createdAt) \(.event)"'
```

If no `schedule` events appear after a few hours, the cron needs replacing with
something that demonstrably runs.

## 7. What the v2026.9.8 release actually proved

The release ran twice. **Both outcomes were informative.**

### Attempt 1 — failed before publishing anything

`Build & Publish` died in `Verify @cleocode/cleo tarball contents`:

```
files[] entry "!dist/**/*.js.map" is MISSING on disk at
  /home/runner/work/cleo/cleo/packages/cleo/!dist/**/*.js.map
```

My defect, from #1482. `assert-cleo-tarball.mjs` treated every `files[]` entry
as a literal path, but npm's `files[]` is a **pattern list** and a leading `!`
is an exclusion. Fixed in #1493: exclusions skip with the reason printed, globs
skip with a `WARN` saying presence is *not* asserted, and the real exclusion
check lives in `check-cleo-tarball-size.mjs`, which runs `npm pack --dry-run`
and verifies against **npm's own resolution** instead of guessing a path.

Nothing published — the gate sits ~300 lines before `pnpm publish`. The tag was
deleted and re-pushed **only after confirming the registry had never seen it.**

> Filed as **gh#1494**: both tarball gates run ONLY in `release.yml`, so a
> defect in either is discovered at publish time. #1482 was green on every check
> that ran; the check that would have caught this does not run on PRs.

### Attempt 2 — published, and the new machinery worked

| | |
|---|---|
| `Build & Publish` | **success** — all 18 accepted |
| `Post-Deploy Payload` | **failure** — verdict `pending`, 17/18 |
| `Release Verdict` | **failure** — `RELEASE NOT VERIFIED INSTALLABLE` |

**That red is correct.** Under the old pipeline this exact state produced a
green run over a missing package, twice.

Everything fired: verdict classified `pending` (not `defect`, not `infra`), the
run went red, tracking issue #1495 auto-created with the do-not-roll-back copy,
the watcher auto-dispatched, and the `publish-timeline-2026.9.8` artifact
appeared.

**The riskiest assumption is now proven in production:** `release-verdict`
(`if: always()`) successfully read outputs from an `execute-payload` job that
had **failed**. It did not fall back to `infra`.

### The sharpest new datum for npm

From the gh#1479 timeline — `cleo`'s publish call **returned in 10.2 seconds**:

```
cleo   PUBLISHED   2026-09-19T01:10:10.143Z → 01:10:20.294Z
                   metadata still 404 at 111 minutes
```

Previously the delay could only be located "somewhere in the publish path". It
is now pinned: **the accept is fast; the registry-side write is what stalls.**
Add this to gh#1478.
